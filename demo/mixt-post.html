tcache 机制分析：从 glibc 2.27 到 2.42 的攻与防

Mixt | 2026-09-01 | 3.5k 字 · 约 14 分钟
合规声明：本文仅用于授权环境下的安全研究。所有分析基于自建靶机与公开 CTF 题目，不涉及任何真实在网目标；文中利用逻辑均以伪代码呈现，关键偏移已打码。

tcache 是 glibc 2.26 引入的线程本地快速缓存，也是堆题绕不开的第一站。这篇笔记按版本演进把它的结构、检测与保护三层拆开看——理解官方每一步补丁的动机，比背利用模板有用得多。

tcache 的数据结构

每个线程一份 tcache_perthread_struct，按 size class 分桶（默认 64 桶，单桶最多 7 块）。管理开销极小：进入 tcache 的块不改 chunk 头，只在用户区写两个指针宽度的字段。

tcache_entry 结构演进（示意） 
/* glibc 2.26–2.28：next 是裸指针，无 double free 检测 */struct tcache_entry {    struct tcache_entry *next;}; /* glibc 2.29+：新增 key，指向所属 per-thread 结构 */struct tcache_entry {    struct tcache_entry *next;  /* 2.32+ 存储时异或（safe-linking） */    uintptr_t            key;   /* double free 检测的依据 */};

key 字段：double free 检测的演进

2.29 之前，同一指针 free 两次就能污染 freelist。补丁的思路很直白：free 进 tcache 时把 key 设成 per-thread 结构的地址，再次 free 同一块时遍历对应桶，发现 key 匹配就报 double free detected in tcache 2。

但检测只覆盖「同一线程同一桶」的路径，于是有了后来各种绕过思路（改写 key、先摘出再 double free 等）——注意，这些思路在本文中只讲条件，不给可直接运行的代码。

safe-linking：指针的异或保护

2.32 起，next 不再明文存储，而是与 chunk_addr >> 12 异或后落盘。效果是两个：

  • 不知道堆地址，就伪造不出合法的 next（leak 变成前置条件）
  • 单纯的部分覆写不再能稳定指向任意位置

伪代码表达存储逻辑就是一行：stored = (pos >> 12) ^ next，取出时反向异或。设计的巧思在于让保护强度依赖「地址本身不可预测」。

小结

把三个版本的补丁连起来看，glibc 的防御是一条清晰的演进线：加字段检测重复释放 → 加异或保护指针完整性。每一次加固都在把「无 leak 的堆利用」往更贵的方向推。下一篇文章打算整理 unsorted bin attack 在新版本下的可用性。
