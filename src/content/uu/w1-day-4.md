## 模块 1 · 迭代协议：iterable 与 iterator 是两个协议

**猜猜看**：`iter(cd)` 返回的是什么？它和 `cd` 是同一个对象吗？`next(it)` 耗尽之后会发生什么？

### ① 现象

```
1) iter(cd) 得到迭代器: CountdownIterator
1) next(it) 三次 = 2 1 0
1) 耗尽后再 next(it) 抛 StopIteration
1) iter(cd) is cd ? False ← 每次 __iter__ 返回新迭代器
```

`iter(cd)` 返回的是一个**新对象** `CountdownIterator`，不是 `cd` 自己。对它连调三次 `next` 依次得到 2、1、0，第四次抛 `StopIteration`。最后一行点破关键：`iter(cd) is cd` 是 `False`——可迭代对象每次 `__iter__` 都**造一个全新的迭代器**出来。

### ② 为什么

Python 的迭代其实由**两个分离的协议**拼成。**可迭代对象（iterable）**实现 `__iter__`，它唯一的工作是返回一个迭代器；**迭代器（iterator）**实现 `__next__`，每次调用推进一个值，耗尽时抛出 `StopIteration` 表示"没有更多了"。脚本里故意写了两个类——`Countdown` 是 iterable（只负责 `__iter__` 返回迭代器），`CountdownIterator` 是 iterator（只负责 `__next__` 推进）——就是为了把这两个协议分开给你看。

为什么迭代器必须是"一次性、有状态"的？因为 `CountdownIterator` 把当前位置存在自己的 `self.current` 上，每 `next` 一次就减一、**丢掉上一个值**。它没有"往回走"的接口，也没有"重新开始"的能力——要重来，只能让 iterable 再 `__iter__` 造一个新的。所以"能不能反复遍历"不取决于对象本身，而取决于它把状态放在哪里：放在**新造出来的迭代器**上就能反复（每次 `__iter__` 都清零重来），放在**自己身上**就是一次性的（模块 5 会讲）。

### ③ C++ 对照

C++ 的迭代器是"广义指针"：你通过 `container.begin()` / `container.end()` 拿到**一对端点**，用 `*it` 解引用、`++it` 前进、`it != end` 判断是否到头。迭代器本身是一个**可拷贝的轻量句柄**——你可以保存一个迭代器、复制一份、随时重新 `begin()`。关键差异在职责划分：C++ 里**容器是数据源、迭代器只是"指向某位置的游标"**，位置信息不垄断在游标里（容器还在，随时能再拿 begin）；Python 里迭代器**自己就是那个装着位置状态的游标**，`next` 推进即改变自身，数据源（iterable）反而不参与推进。

另一个差异是"结束"的表达：C++ 用 `it != end` 这个**哨兵比较**判断终点，比较的是两个游标是否指向同一位置；Python 没有 end 哨兵，用**抛异常**（`StopIteration`）表达"没了"。前者是返回值层面的判断，后者是控制流层面的跳转。

| 想做的事 | Python 写法 | C++ 对应 |
|---|---|---|
| 得到迭代器 | `it = iter(obj)`（调 `__iter__`） | `it = c.begin()` |
| 推进并取值 | `next(it)`（调 `__next__`） | `*it` 后 `++it` |
| 判断是否结束 | 捕获 `StopIteration` | `it != c.end()` |
| 重新开始遍历 | 再 `iter(obj)` 拿新迭代器 | 再 `c.begin()` |

### ④ 坑与适用

最常见的坑是**把两个协议混成一个类**：为了省事，让 `__iter__` 返回 `self`、又在同一个类里实现 `__next__`。这么写出来的对象第一次 `for` 正常，第二次 `for` 就空了——因为它是自己的迭代器，状态留在自己身上，遍历一次就耗尽。判断标准就是脚本最后一行那句 `iter(cd) is cd`：**返回 `True` 说明这个对象是一次性的**（是迭代器而非"纯 iterable"），返回 `False` 才是每次新造迭代器的正常可迭代对象。

适用面反过来也清楚：如果你要的本来就是一个"只能消费一次的游标"（比如读取网络流、遍历一次性的数据源），那 `__iter__ return self` 是合理的；但要的是可反复遍历的容器，就必须把状态放进每次新建的迭代器对象里。这个取舍在 W4 写 SSE 解析时会直接决定代码结构——流只能读一遍，解析器就是一个天然的一次性迭代器。

## 模块 2 · `for` 循环 = `iter` + `next` + 捕获 `StopIteration`

**猜猜看**：`for n in Countdown(2)` 这一句，背后解释器做了什么？能不能用 `while` 把它**完整**重写出来？

### ① 现象

```
2) for 里拿到: 2
2) for 里拿到: 1
2) for 里拿到: 0
2) 上面的 for 等价于这段手工展开: [2, 1, 0]
```

`for` 循环依次拿到 2、1、0；下面那段 `while` + `try/except StopIteration` 的手工展开，得到**一模一样**的结果 `[2, 1, 0]`。

### ② 为什么

`for` 循环不是语法魔法，它是对**上一模块两个协议**的固定调用序列。解释器遇到 `for n in obj`，先 `it = iter(obj)` 拿迭代器，然后进入循环：每次 `next(it)` 取值赋给 `n`、执行循环体，直到某次 `next(it)` 抛 `StopIteration`，就静默捕获、退出循环。脚本里那段 `while True` 就是把这个过程一字不差地写了出来——`iter`、`next`、`except StopIteration: break`，三件事一一对应。

这件事的意义比看起来大：它说明 Python 的 `for` 是一个**运行时协议**，不是编译器写死的语法。只要一个对象实现了 `__iter__`（返回一个会 `__next__` 的东西），`for` 就能遍历它——不管它是列表、字典、文件、还是你自己写的类。这种"按协议适配、而非按类型适配"的能力，就是鸭子类型在循环上的体现。

### ③ C++ 对照

C++ 的 range-based for 是**编译期语法糖**：`for (auto& x : c)` 被编译器在编译阶段展开成 `for (auto it = begin(c); it != end(c); ++it)` 那一套。整个过程发生在编译器内部，运行时没有"for 协议"这种东西——你没法在运行时"模拟"一个 range-for，因为展开早就在编译时完成了。Python 的 `for` 恰好相反：它是运行时可复现的协议调用，所以你能用 `while` 手动重放一遍，分毫不差。

这个差异带来一个实际后果：Python 里任何类型都能通过实现 `__iter__` 被 `for` 支持，而且**运行时可替换**；C++ 里 range-for 支持什么类型，由编译期对 `begin`/`end` 的约束决定，是静态的。两者都是"统一遍历接口"，但一个靠运行时协议、一个靠编译期展开。

### ④ 坑与适用

坑：自己写 `__iter__` / `__next__` 时，如果 `__next__` 忘了在耗尽时抛 `StopIteration`，`for` 循环会变成**死循环**（因为 `for` 靠这个异常退出）；反过来，如果 `__next__` 在还没耗尽时就抛了，循环会**提前静默终止**、不报任何错。两个方向都很难排查，因为 `for` 把异常吃掉了，不留痕迹。

适用：理解这个展开之后，"为什么能对文件对象、字典、甚至 `zip`/`enumerate` 的结果直接 `for`"就不需要死记了——它们都实现了 `__iter__`。这也给了你一个调试手段：看到某个对象能被 `for` 遍历却不知道它内部怎么迭代，`iter(obj)` 拿迭代器、手动 `next` 几下，行为立刻现形。

## 模块 3 · 生成器：`yield` 把函数变成迭代器

**猜猜看**：调用一个包含 `yield` 的函数，会发生什么？函数体里的代码会执行吗？返回值是什么？

### ① 现象

```
3) 调用生成器函数得到: generator （函数体一行都没执行）
3) next(g) 三次 = 2 1 0
```

调用 `countdown_gen(2)` 没有执行函数体——它返回一个 `generator` 对象。之后对 `g` 调 `next`，才依次得到 2、1、0。注意 `countdown_gen` 里用的是 `while start >= 0: yield start; start -= 1`——但这段循环**一次都没跑**，直到你开始 `next`。

### ② 为什么

`yield` 改变了函数的根本性质：只要函数体里出现 `yield`，这个函数就不再是普通函数，而是**生成器函数**。调用它不会执行函数体，只返回一个 generator 对象——这个对象内部封装了"函数体 + 执行到哪里了"的状态。每次 `next(g)`，函数体从**上次 `yield` 暂停的地方**继续执行，运行到下一个 `yield`，把 `yield` 后面的值交出来，然后**再次暂停**，记住这次停在哪。循环往复，直到函数体跑完（`return` 或自然结束），才抛 `StopIteration`。

所以生成器本质上是一个**编译器帮你写好的迭代器**：模块 1 里你要手写 `CountdownIterator` 类、用 `self.current` 手动存状态、手动 `__next__`——现在 `yield` 让你用**普通函数的样子**写这段逻辑，解释器自动把"当前位置"翻译成隐式状态保存起来。写生成器比写迭代器类省掉一整个状态管理，这是它最大的价值。

### ③ C++ 对照

标准 C++ **没有生成器**。要表达"惰性序列"，你得手写一个迭代器类——保存状态、实现 `operator*` / `operator++` / `operator!=`，和模块 1 的 `CountdownIterator` 是同一套手工活。C++20 引入了协程（`co_yield`），C++23 才进标准库 `std::generator`，但主流工具链和项目里远未普及——所以按你现在的 C++ 经验，对应物就是"手写迭代器"。

更深一层：C++ 普通函数是"要么一次跑完、要么返回"，执行流没有"中途暂停、下次接着跑"的语义（除非上协程）；Python 的 `yield` 天然提供了这个能力。今天先把它当"写迭代器的省力工具"理解就够了，但记住这个"可暂停函数"才是真正的大杀器——W3 讲协程时，`async`/`await` 就是在同一个"可暂停/恢复"的机制上再长出来的。

| 想做的事 | Python 写法 | C++ 对应 |
|---|---|---|
| 手写一个迭代器 | 写 `__iter__`/`__next__` 类 | 写迭代器类（`*`/`++`/`!=`） |
| 用函数写迭代器 | `def f(): ... yield x` | C++20 `co_yield` / C++23 `std::generator`（未普及） |
| 暂停/恢复执行流 | `yield` 天然支持 | 需协程 |

### ④ 坑与适用

坑一：**误以为调用生成器函数会执行函数体**。写了 `countdown_gen(2)` 却不消费它，函数体一个字都不会跑——如果你在函数体里放了"有副作用的初始化"（开连接、读配置），它会**延迟到第一次 `next` 才发生**，时机比你以为的晚得多。坑二：`yield` 一旦出现，函数就**整体**变成生成器，`return` 不能再带普通值（`return x` 在生成器里是"结束"而非"返回 x"）——这类语义差异在 W3 会更明显。

适用：凡是"按需产生、不必一次算全"的场景，生成器都是首选——处理大文件逐行读、逐条流式解析、生成无限序列（`yield` 无限循环配合 `for` 截断）。W4 的 SSE 事件流解析，本质就是"一个生成器，每次 `yield` 一条完整事件"。

## 模块 4 · 惰性求值：生成器只在需要时才算

**猜猜看**：`ls = lazy_squares(3)` 这行调用，会打印出函数体里那几句 `print` 吗？什么时候才会打印？

### ① 现象

```
4) 列表推导：调用即算完整个列表
4) 调 lazy_squares(3)（注意：下面这行调用没有任何输出）→
4) 第一次 next(ls)，函数体这时才动 →
4)   函数体开始执行（由第一次 next 触发）
4)   现在才真正算 i=0
4) next(ls) = 0
4)   现在才真正算 i=1
4) next(ls) = 1
```

`eager_squares(3)` 一调用就打印"列表推导：调用即算完"——整份结果当场算好。而 `ls = lazy_squares(3)` 这行**调用本身没有任何输出**：函数体里那句"函数体开始执行"没出现。直到第一次 `next(ls)`，函数体才动起来，打印"现在才真正算 i=0"、返回 0；第二次 `next` 才轮到 i=1。

### ② 为什么

"惰性"指的是**把计算推迟到真正需要结果的那一刻**。列表推导 `[i*i for i in range(n)]` 是**急切的**：表达式一求值，就把整个列表算完、存进内存，所以函数一调用那句 `print` 就立刻执行。生成器是**惰性的**：`lazy_squares(3)` 只返回一个 generator 对象，函数体被"冻结"在起点；每次 `next` 才解冻一步、算一个值、在 `yield` 处再冻住。脚本里函数体内的两处 `print` 就是探针——它们出现的时机，直接证明了"调用不执行、`next` 才执行"。

这个差异的代价与收益是对称的：急切版本一次算完，代价是**立刻占用全部内存、且必须等待全部算完**才能用第一个值；惰性版本每个值都现算，代价是**每次取值有函数调用的开销**，但收益是内存 O(1)、且能"边算边用"——第一个值不用等后面的。对"先来先用"的流式场景，惰性是唯一正确解。

### ③ C++ 对照

C++ 里"物化"和"惰性"是两套显式的选择。默认是物化：`std::vector<int> v; for(...) v.push_back(i*i);` 一次性算完存好。想要惰性，要么手写迭代器（模块 3 那套），要么用 C++20 ranges 的**惰性 view**——`views::transform` 之类的东西直到你遍历它才逐项计算。所以两边结构其实是对称的：**C++ 的 vector 对应 Python 的列表推导（急切、物化），C++ 的 view 对应 Python 的生成器（惰性、不物化）**。差异只在默认值——Python 里你写列表推导得到的是急切，想惰性要显式用生成器表达式/生成器函数；C++ 里你写 vector 是急切，想惰性要显式用 view。两边都不是默认惰性。

| | Python | C++ |
|---|---|---|
| 急切（一次算全、占内存） | 列表推导 `[i*i ...]` | `std::vector` 物化 |
| 惰性（按需算、O(1) 内存） | 生成器 / 生成器表达式 | ranges 惰性 view / 手写迭代器 |
| 默认倾向 | 列表推导常见（急切） | vector 常见（急切） |

### ④ 坑与适用

坑：**把生成器当列表用**。比如对生成器取 `len()`、按下标访问、重复遍历（模块 5）——全都失败或行为异常，因为生成器不实现 `__len__`、不支持索引、且是一次性的。这类错误常见于"本来是列表、后来为省内存换成生成器"的重构——换完 `len()` 直接 `TypeError`。坑二：惰性把副作用推迟了，如果生成器函数体里有"打开资源/建立连接"，它会在你不经意的 `next` 里才发生，出错堆栈离你"创建"它的地方很远。

适用：数据量未知或超大、只需要顺序消费一次、或者希望"尽早拿到第一个结果"的场景。Day 4 的自查题"生成器表达式为什么省内存"答案也在这里——因为它根本不把整个序列存下来，任何时候只保留当前一个值。W4 解析 SSE 流时，服务器可能无限地发事件，你必须惰性、边收边解，这条就是直接铺垫。

## 模块 5 · 生成器只能消费一次

**猜猜看**：对同一个生成器 `for` 遍历两次，第二次会得到什么？换成 list 呢？

### ① 现象

```
5) 第一次遍历: [1, 0]
5) 第二次遍历: [] ← 空，已经耗尽
5) list 可反复遍历: [1, 0] | [1, 0]
```

同一个生成器 `g`，第一次遍历得到 `[1, 0]`，第二次得到**空列表**。换成 list，两次遍历都得到 `[1, 0]`——可反复。

### ② 为什么

生成器（以及一切迭代器）是**单次推进的游标**：位置状态存在自己身上，每产出一个值就向前走一格，走到头就停在"耗尽"状态。第一次 `for` 遍历把 `g` 从头推到尾，耗尽后它**停在终点**；第二次 `for` 再从它身上 `iter()`，拿到的是**它自己**（生成器的 `__iter__` 返回 self），而它已经在终点了，所以一个值都拿不到，直接 `StopIteration`。这就是模块 1 结尾那句 `iter(cd) is cd` 的反面教材——生成器天生是"自己是自己的迭代器"，所以一次性。

list 之所以能反复遍历，是因为它是**纯 iterable**：`iter(list)` 每次都造一个**新的** `list_iterator`，从头开始。数据源（list）本身不承载遍历位置，位置在新造的迭代器上。所以"能不能反复遍历"的判据又回到模块 1：**位置状态放在迭代器（每次新建）上就能反复，放在自身（`__iter__ return self`）上就一次性**。生成器属于后者。

### ③ C++ 对照

C++ 的迭代器（至少 forward iterator 及以上）是**可拷贝的**：你遍历一遍后，还能再 `begin()` 拿新迭代器，或者干脆把某个迭代器 `auto it2 = it;` 复制一份分别推进。容器是数据源，只要容器还在，随时能重新开始——所以"遍历消耗了数据"这个概念在 C++ 里不存在（除非你遍历时边读边删容器）。Python 的迭代器是**有状态的单次游标**，推进即消耗，没有"复制游标"这条路（生成器更没法复制）。根源还是那句：C++ 把位置做成可拷贝句柄，Python 把位置做成对象内在状态。

### ④ 坑与适用

坑一：同一个生成器被**两个 `for` 循环或两个消费者**交替使用时，第一个会把值拉走，第二个只能拿到剩下的——这类"隐性状态共享"的 bug 在把生成器当参数传给多个函数时尤其隐蔽。坑二：把生成器赋值给变量后、过一会儿再消费，中间如果已经被别处消费过，结果就"莫名其妙少了几个值"。排查口诀：**凡是"结果比预期少/空"的迭代问题，先问这个对象是不是已经被人 `next` 过了**。

适用：反过来，**"只能消费一次"正是流式数据的天性**——网络流、文件句柄、实时事件本来就是一次性资源，生成器这个行为恰好匹配。想要"能重放"的序列，就**物化成 list**（一次性算完、存起来、反复读），或者保留"能重新造生成器的工厂函数"，每次要遍历时调工厂拿个新的。两种需求、两种选型，别混。

**对应条目**：#15 生成器只能消费一次

## 模块 6 · `yield from`：委托给子生成器

**猜猜看**：`outer_delegated` 里写 `yield from inner()`，和手写 `for item in inner(): yield item` 有什么差别？

### ① 现象

```
6) 手写 for+yield : ['a', 'b']
6) yield from 委托: ['a', 'b']
6) yield from 也能委托任意可迭代对象: [1, 2, 3, 4]
```

手写循环转发和 `yield from` 得到一模一样的结果 `['a', 'b']`。最后一行证明 `yield from` 不只接生成器，还能直接接列表 `[1, 2]`、元组 `(3, 4)` 等任意可迭代对象，拼出 `[1, 2, 3, 4]`。

### ② 为什么

`yield from inner()` 的字面意思就是"把我暂停在这里，把控制权整个交给 `inner()`，它 yield 什么我就**原样转交**什么，它结束了我再从这行继续"。在最简单的只读场景下，它确实等价于 `for x in inner(): yield x`——两者都在做一个"转发"的动作，所以第一、二行输出相同。

但 `yield from` 不是语法糖那么简单，它做的是**双向委托**：它不只把内层生成器产出的值向上转发，还把外面对它的 `send()`（往里传值）、`throw()`（往里抛异常）、`close()`（关闭）**原样转发给内层**，同时内层返回的值（`return` 的值）也能被外层 `yield from` 的左边接收。这一整套"上下行都打通"的机制，是手写 `for + yield` 转发不了的——`for` 循环只转发"产出"，不转发"send/throw/close"。今天脚本里只用到了只读的那一半（所以看起来和 for+yield 一样），双向的那一半是 W3 讲生成器协程时的核心。

### ③ C++ 对照

C++ 没有 `yield from` 的对应物。C++20 协程的 `co_yield` 只负责"往上一层交一个值"，没有"把控制流整体委托给另一个协程/生成器"的语法；要转发，只能自己写循环 `for (auto&& x : gen) co_yield x;`——恰好对应 Python 里那个"手写 for+yield"的笨办法。所以 `yield from` 是 Python 生成器模型里 C++ 目前没有的那一块：它让生成器可以**组合**（一个生成器把活派给一群子生成器），而不必在一个函数里写平。这个"组合"能力，是 Python 里"生成器管道"（层层 yield from 串起处理链）能写得很顺的原因。

### ④ 坑与适用

坑：读代码时**误把 `yield from` 当成"调用一个函数拿返回值"**。它不是在 `inner()` 的结果上做什么，而是把整个控制流**停在这里、让内层接管**——内层产出的每一个值都会从外层这里冒出去。如果内层是个无限生成器，外层也就跟着永远停不出来了。坑二：`yield from` 后面必须接可迭代对象，接个普通值（`yield from 5`）会 `TypeError`——要产出单个值得用 `yield`，不是 `yield from`。

适用：扁平化嵌套结构（遍历嵌套列表时 `yield from` 摊平一层）、把大生成器拆成若干小生成器再组合、以及"代理"模式（外层生成器包一层，转发给内层实现）。在 W3 的协程上下文里，`yield from` 的 send/throw 双向转发会让它成为构建协程管道的骨架——今天先记住"它是委托、不是普通调用"就够。

**对应条目**：#16 `yield from`

## 模块 7 · 生成器表达式：惰性、省内存

**猜猜看**：`(i * i for i in range(3))` 和 `[i * i for i in range(3)]` 只差一对括号，但一个是生成器一个是列表——内存占用差多少？

### ① 现象

```
7) 生成器表达式得到: generator
7) 消费一次: [0, 1, 4]
7) 再消费一次: [] ← 空（同模块 5，一次性）
7) 列表推导对象占用: 800984 字节（10 万元素都持有）
7) 生成器表达式占用: 200 字节（不随元素数增长）
```

把方括号换成圆括号，得到的就是一个 `generator`，消费一次得到 `[0, 1, 4]`，再消费就是空（继承模块 5 的一次性）。内存对比最扎眼：10 万元素的列表推导对象占约 **78 万字节**，同样 10 万元素的生成器表达式只占 **200 字节**——差了近四千倍，而且生成器的这个 200 字节**不随元素数增长**。

### ② 为什么

生成器表达式就是**生成器函数的简写**：`(i*i for i in range(3))` 等价于一个内部"`for i in range(3): yield i*i`"的匿名生成器。它继承生成器的全部属性——惰性（调用不计算）、一次性（消费即空）、O(1) 内存。列表推导则是**急切物化**：表达式一求值，就真的把 10 万个平方值算出来、存进一个 list 对象里。

那 78 万字节 vs 200 字节的差距从哪来？列表对象要**同时持有全部 10 万个元素**，`sys.getsizeof` 测到的就是它那 10 万个指针槽（每个约 8 字节）加上对象开销。生成器对象只保存"当前的执行位置 + 局部变量 + 迭代到哪了"，和"还有多少元素没算"无关，所以永远是那 200 字节上下。**惰性的本质就是"不保存未产生的值"**——这个内存差异是惰性最直观的收益。

> 补一个诚实的细节：`sys.getsizeof` 只算对象**本身**的浅层大小，列表里那 10 万个 `int` 对象本身的字节它没算进去（int 对象另有开销）。所以真实差距比 78 万 vs 200 还要**更大**。但方向是确定的：列表内存 O(n)，生成器内存 O(1)。

### ③ C++ 对照

C++ 里同样一对概念是**物化容器 vs 惰性 view**：`std::vector<int>` 把 10 万个平方算好存起来（对应列表推导，O(n) 内存），`ranges::views::transform` 之类则是一个"配方"，直到你遍历才逐项算（对应生成器表达式，O(1) 内存）。两边语义完全对齐：**括号/容器选型，就是"要不要现在就把结果算出来存着"的决策**。C++ 里物化 vector 是默认顺手的选择，惰性 view 要显式引入 ranges；Python 里列表推导是默认顺手的选择，惰性要显式用圆括号的生成器表达式——又是"默认都偏急切、惰性都要显式"的对称。

### ④ 坑与适用

坑：生成器表达式**一旦定义就绑定变量、但延迟取值**——如果它引用的循环变量/外层变量后来变了，取值时会拿到变化后的值（这和 Day 3 模块 5 的晚绑定是同一个机制）。另一个坑是把它当列表用：`(i*i for i in ...)` 不支持 `len`、索引、两次遍历，直接复用模块 5 的"一次性"结论。第三个坑是**生成器表达式作为唯一实参时可以省略外层的圆括号**（`sum(x*x for x in ...)`），但一有别的参数就必须带括号——这类语法细节容易写错。

适用：最典型的就是**不落地的大数据流水线**——`sum(x*x for x in huge_range)` 里，生成器表达式让 `sum` 边取边累加，全程只有一个值在内存里，而 `sum([x*x for x in huge_range])` 会先造出整个大列表再求和。W4 的流式处理会把这条用到极致：一个"逐条产出事件"的生成器，接一串"逐条变换"的生成器表达式，数据从头到尾**不整体落地**。

**对应条目**：#14 生成器与惰性求值
