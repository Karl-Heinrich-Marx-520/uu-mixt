**由第一轮推导出的三个关键结论**

1. **未备案 + 等备案上线** → 开发期无需为访问方式妥协，M7 可直接上标准 443；但上线时间受备案周期（7–20 天）约束，需倒排。
2. **翻转 + 一人一路由** → 隔离必须落在信息架构层，翻转只是视觉外化。
3. **两位作者不熟 web + 2C2G** → 只能走静态生成 + 手动部署；任何常驻服务与数据库被否决，"轻量后台"降级为扩展项。

| 提问 | 结论 |

### 1.5 第四轮：一处因果误判（重要）

原始反馈是"双远端方案太麻烦了，干脆不要评论区了"。这条推理链在第二环断了：

| 误判 | 实际 |
|---|---|
| "giscus 要 GitHub → 所以要搞双远端 → 太麻烦 → 砍评论区" | **双远端的复杂度来自"部署方式"的选择，与用什么评论系统没有因果关系。** 换成任何评论系统、甚至完全不要评论，部署该配的一样要配 |

**结论**：砍评论区换不来部署简化，它只是少了一个成本近乎为零的功能。最终的评论区决策另有三条产品层面的理由（见 2.4）。

### 1.6 第五轮：三个提问

| 提问 | 结论 |
|---|---|
| 私有仓库更简单吗 | 是，但简单在**写作流程**（草稿可放心提交），**与部署复杂度无关** |
| GitHub 不方便访问吗 | 是真实成本，但影响范围有限（见 2.5） |
| 放服务器上不行吗 | 行，此前论证说重了（见 2.2） |

## 2. 关键决策的完整论证

### 2.1 技术栈选型

**背景约束**：服务器 2 vCPU / 2GB；两位作者均不熟悉 web 前端。

| 否决项 | 原因 |
|---|---|
| Next.js SSR 常驻 | 空闲内存约 180MB，构建峰值 800MB–1.5GB，2GB 机器上大概率 OOM |
| 数据库驱动的内容管理 | 与"本地 Markdown + 手动部署"链路冲突，制造双真相源 |
| Docker 化 | 守护进程自身约 120MB（2GB 的 6%），单站点无收益 |
| 重量级动画库 | 翻转只需 `transform` + History API |
| 任何自建评论后端 | 与"零运维"目标冲突 |

**采用 Astro 的三条理由**

1. **frontmatter schema 强校验** —— 对不熟 web 的人是安全网：写错字段会在构建时报错并指出位置，而非静默产出坏页面
2. **内置 RSS / sitemap / 内容集合** —— 不用自己写
3. **islands 架构** —— 只有翻转与入场组件加载 JS，其余是纯静态 HTML

### 2.2 仓库托管位置（含两次论证修正）

**最初论证（v0.4，后被修正）**：自建仓库会失去两项能力 —— PR 审核（裸仓库无 PR，补回需 Gitea 约 150–200MB 常驻）与异地备份（单台 ECS 是单点）。

**修正后（v0.5）**：两条都比原先弱。

| 原先的论证 | 重新评估 |
|---|---|
| 失去 PR 审核 | 真正需要 PR 的场景只有"合写文章"与"改共享外壳"，**一年可能仅数次**。这种频率完全可用更土的办法替代：建分支 → 对方 `git fetch` 看 diff → 线下确认 → 合并 |
| 失去异地备份 | 两人各自本地都有 clone，实际已有 3 份副本，服务器磁盘故障不会丢内容 |
| 失去评论载体 | 评论区已确定首期不做，该理由自动失效 |

**自建仓库真正的代价**（这才是决策依据）：需要开 SSH 账号并配权限、没有 Web 界面看历史与 diff、服务器上多一个需要知道"它在哪、要不要备份"的东西。

**最终采用 GitHub 的两条理由**

1. **协作管理成本最低** —— 邀请协作者点一下即可（免费个人账号私有仓库协作者无上限）
2. **一处外部副本** —— 仓库放 GitHub 等于自动获得一处不在自己手里的备份

**一条可复用的判断**：GitHub 在这个项目里承担的角色**不是"托管代码"，而是"协作平台 + 一处外部副本"**。

**服务器自建仓库的退路记录**（技术上可行，仅当 GitHub 体验不可忍受时启用）：push 秒完成、数据完全自主。若两人共用一个受限 SSH 账号 push，服务器层面看不出是谁推的，但 **git 提交中的 author 仍是各自的**，署名与归属照样清晰，还省掉一套权限配置。

### 2.3 部署方式的兴废（双远端的教训）

**v0.3 曾推荐**：双远端（GitHub + 服务器裸仓库）+ post-receive 钩子 + 推送即上线。卖点是"部署即版本、可回滚"。

**已否决，理由**：

| 否决理由 | 说明 |
|---|---|
| 一次性配置成本前置 | 需在服务器上建裸仓库、写钩子脚本、管理部署分支 |
| **失败是静默的** | 钩子脚本出错时 `git push` 仍会成功返回，站点却没更新。对不熟 web 的人是"不知道哪里错了"的故障 |
| 收益可以更便宜地获得 | 其"部署可回滚"对静态站点价值很低：本地有全部历史，重新构建并部署上一次产物约 30 秒 |
| 多引入一套概念 | 需要理解"裸仓库 / 部署分支 / 钩子"，而手动上传的心智模型就是"把一个文件夹同步过去" |

**最终采用**：单远端 + 一条命令手动上传。选择它的主要好处恰是**失败可见**。

**代价**：部署层面失去回滚兜底 → M0（`git init`）的重要性显著上升，建议 M1 启动前完成。

### 2.4 评论区（三轮演进）

| 阶段 | 结论 | 理由 |
|---|---|---|
| 原始需求 | 匿名评论区、无登录限制 | — |
| 第二轮 | 放弃匿名，改用 giscus | 见下方"匿名冲突" |
| **现行** | **首期不做** | 产品层面的三条理由见下 |

**匿名冲突的完整说明**

| 项 | 内容 |
|---|---|
| 冲突约束 | 服务器无后台、无数据库、无常驻进程 |
| 冲突说明 | giscus 类零后端方案**强制 GitHub 登录**，无法提供匿名；真正匿名必须有一个能写入数据的服务端 |
| 附加风险 | 匿名评论无登录门槛 → 机器人灌水成本为零；中国独立博客评论区通常在**上线后数周内**被扫描到，需人工删除；连带产生防刷、备份、内容审核三项运维负担 |

**首期不做的三条理由（产品层面，与部署无关）**

1. 个人技术博客在没有外部引流时，绝大多数文章的评论数为 0（预期半年内只收到个位数评论）
2. 页面挂一个"暂无评论"的空区域，观感比没有评论区更差
3. 评论是纯增量功能，不做它不影响任何已有设计，日后随时可加

**日后加入路径**：giscus，需另建一个公开仓库并开启 Discussions。加入时机为出现第一篇外部读者主动提问时。

**若日后重新考虑匿名**：① 由 UU 用 Boost.Beast 自建极简评论 API（内存 10–20MB，可作为练手项目，但需自行承担防刷/备份/安全）；② Disqus（支持匿名，但国外服务、国内加载慢、有广告与隐私争议）。

### 2.5 公开仓库 vs 私有仓库

| 维度 | 公开 | 私有（采用） |
|---|---|---|
| 草稿保密 | ❌ 提交即对外可见，需要 `_drafts/` 纪律 | ✅ 草稿可放心提交，**取消一条纪律** |
| PR 与 Issues | ✅ | ✅ 同样支持 |
| 协作者数量 | 无上限 | **免费个人账号下同样无上限**，两人无障碍 |
| 分支保护 / 强制 review | ❌ 属 Pro 功能 | ❌ 同左 |
| 日后作评论载体 | ✅ | ❌ 需另建公开仓库 |
| 对外展示 | ✅ | ❌ 但面试官看的是网站，不是仓库 |

**选择私有带来的实际简化**：写作流程上取消"草稿必须放 `.gitignore` 的 `_drafts/` 目录、绝不提交"这条纪律。**注意：这与部署复杂度无关。**

**GitHub 访问不稳定这一代价的影响边界**

| 动作 | 是否受影响 |
|---|---|
| 读者访问网站 | ❌ 完全不受影响（网站从自己服务器出） |
| 本地写文章、`git commit` | ❌ 不受影响（Git 是分布式的） |
| `git push` / `pull` | ✅ 可能慢或超时。但属低频动作，失败可重试，不阻塞工作 |

### 2.6 备案与端口

| 事实 | 说明 |
|---|---|
| 未备案的封禁范围 | 大陆地域 ECS 未备案时默认封禁 80/443，**与是否绑定域名无关**（用公网 IP 直连 80 同样不通） |
| 非标准端口 | 8080 / 8888 等短期可用，但存在被扫描后封禁的风险 |
| 对架构的影响 | 无。端口只是 Nginx 监听配置的一行差异，正式上线改为 443 即可 |
| 域名限制 | 域名只允许字母、数字、连字符，因此站点名 `UU&Mixt` 无法直接作为域名，映射为 `uuandmixt.com` |

> 来源说明：以上为多份二手资料的共识，官方口径应以阿里云备案控制台为准。

### 2.7 入口页形态与动效取舍

**形态演进**：从"二选一的门"确定为"两卡并立 → 收拢重叠 → 整叠翻转 → 放大入场"。

**动效参数的选择依据**

| 参数 | 取值 | 依据 |
|---|---|---|
| 时长 720ms | 翻转 | 短于 500ms 显得仓促，长于 900ms 会烦 |
| 缓动 `cubic-bezier(0.22, 0.61, 0.36, 1)` | ease-out-quad | 起步果断、收尾平缓 |
| 暴露 2400px | 透视 | 过小会畸变，过大则看不出立体 |
| 中点 `scale(0.94)` | 景深 | 制造"离开"的纵深感，是"帅"的主要来源 |
| 只动画 `transform` / `opacity` | 性能 | 动画 `width` / `color` 会触发重排 |

**明确不做**：模糊、发光、渐变叠加、粒子。理由：显著增加合成层负担，低端机直接掉帧。

**S1 的视觉关键**：未选中的卡片必须从选中卡左上错出 10–14px 保留边缘可见 —— 这是"另一面仍然存在"的视觉暗示，不可省略。

**二次访问必须跳过入场动画**：1.7 秒的仪式第一次看很帅，第二次就是骚扰。

### 2.8 内容管理系统：轻量后台的降级

原始需求是"Markdown + 轻量后台"。**后台被降级为扩展项**，理由：链路是"本地写 Markdown + 手动部署"，后台没有写入对象 —— 它唯一能做的写操作会与本地文件产生两个真相源。两位作者都不熟 web，多一个常驻服务就是多一个半夜会挂的东西。

| 后台的原始价值 | 替代方案 |
|---|---|
| 防止元数据写错 | 构建期 schema 校验，报错更精确 |
| 防止分类拼错 | 构建期分类校验 |
| 在线快速记录想法 | 手机便签，回到电脑再整理成文 |

**将来若确实需要**：Decap CMS（Git-based，无数据库，构建期生成的静态管理界面），直接向 Git 仓库提交 Markdown，与现有链路完全兼容。

### 2.9 站内 AI 助手（桌宠）的架构影响

**这不是一次扩展，而是第二个产品。** 它会把项目从"零运维静态站"变成"有一个需要监控计费与滥用的服务"。

| 环节 | 纯静态站能否承载 | 需要的补充 |
|---|---|---|
| 文章切块与向量化 | ✅ 构建期完成 | 构建脚本调用 Embedding API（一次性成本） |
| 向量存储与检索 | ✅ 可静态化 | 向量存为静态 JSON，前端本地算余弦相似度（文章数 < 500 时可行） |
| 生成回答 | ❌ | 需 LLM API；**API Key 不能放前端** → 需要一个转发端点 |
| 桌宠形象与交互 | ✅ 纯前端 | SVG/CSS 立绘 + 对话气泡，需可关闭、不阻塞首屏 |

**架构影响**：新增一个 LLM API 转发端点（Serverless 或自建极简代理，内存 < 20MB）；新增按 token 计费的成本；**必须限流**，否则匿名用户可刷 API 额度；内存预算需预留约 200MB。

**建议的两步走路线**

| 阶段 | 做法 | 成本 | 目的 |
|---|---|---|---|
| 第一步 | 只做相似度检索 + 返回文章摘要，不调用 LLM | 零 API 成本 | 验证是否真的有人点它。若一个月内使用量接近零，第二步就不该做 |
| 第二步 | 加转发端点 + 限流 + 计费监控，把检索结果拼进 prompt 生成回答 | 按量计费 | 在第一步验证有真实需求后 |

## 4. 被否决方案速查表

| 被否决 | 一句话原因 |
|---|---|
| Next.js SSR 常驻 | 构建峰值内存超出 2GB 机器承受范围 |
| 数据库驱动的 CMS | 与本地 Markdown 链路冲突，制造双真相源 |
| Docker 化 | 守护进程内存占用不划算 |
| 重量级动画库 | 翻转只需 transform + History API |
| 服务器自建 Git 仓库 | 协作管理成本高于收益（见 2.2） |
| 双远端推送部署 | 失败静默（见 2.3） |
| 公开仓库 | 草稿无法保密（见 2.5） |
| 匿名评论 | 与"无后端"硬约束冲突，且带来灌水与审核负担（见 2.4） |
| 自建评论后端 | 与零运维目标冲突 |
| 首期做评论区 | 产品层面理由（见 2.4） |
| Disqus | 国外服务、国内加载慢、有广告与隐私争议 |
| 自建内容管理后台（数据库 + 常驻服务） | 与"无服务器端常驻进程"硬约束冲突，且产生双真相源；改用 Decap CMS（见 7.2） |
| 在线写作由 UU 代为提交 | 与产品目标 G6"Mixt 独立发文"冲突（见 7.2） |
| 教 Mixt 使用 git | 与"Mixt 不接触代码与命令行"冲突（见 7.2） |
| ECS 按使用流量计费 | 属**静默失败**：被刷流量时不报错、不告警，只在月底账单上体现（见 7.4） |
| 主导航栏放"关于本站"入口 | 站点的视觉重心在两面，导航栏加公共项会稀释"两面隔离"的观感；改为入口页底部一行小字（见 7.5） |
| 多语言 | 无此需求 |

## 6. 通用教训

### 6.1 给"不熟 web"的人做选型，"失败是否可见"比"功能是否更强"更重要

来源：双远端方案被否决。它的致命缺陷不是配置复杂，而是**钩子失败时 `git push` 仍返回成功** —— 属于静默失败。对手动上传而言，失败会直接报错。

### 6.2 不要把两件独立的事用一条因果链拴起来

来源：第四轮的"giscus 要 GitHub → 所以要搞双远端 → 太麻烦 → 砍评论区"。部署复杂度与评论系统无因果关系。**遇到"因为 A 所以 B 所以只好放弃 C"的推理，先检查每一环是否真的成立。**

### 6.3 用户反复追问的问题，往往说明前一次的回答论证不足

来源：仓库托管位置被问了两次（第三轮、第五轮），第二次才发现第一次的论证站不住。**被追问时先假设自己错了，重新评估，而不是重复原结论。**

## 7. 2026-09-13 的产品级决策

### 7.1 协作模型由对称改为不对称

**用户明确**：Mixt 不参与网站搭建，只上传文章。

**影响与处理**

| 层面 | 变化 |
|---|---|
| 产品层（分栏自治、两面隔离） | **不变** —— 这是产品需求，与谁做工程无关 |
| 建设层 | 由"两人共同维护"改为"UU 独任工程 + Mixt 仅内容" |
| 原有的权限矩阵 | 失效：它的写法假设 Mixt 会碰工程文件 |
| 原有的审核约定 | 失效：它的写法假设 Mixt 会走 PR 流程 |

**为什么没有推翻分栏自治**：分栏自治解决的是"两位作者的内容如何互不干扰"，而不是"谁来做开发"。两者是不同维度，因此产品约束保留、协作约束重写。

### 7.2 网页上传入口（Decap CMS）由扩展项提升为首期必备

**用户选择**：Mixt 通过**网页入口**上传文章（而非由 UU 代为提交，也非教他使用 git）。

**这个选择的连带后果**（必须记录，否则容易被当成"加个页面"）

| 后果 | 说明 |
|---|---|
| 产生新的产品目标 | G6：Mixt 无需接触代码与命令行即可发文 |
| 产生新的里程碑 | M5 网页上传入口，且必须在 M8 上线之前完成，否则 Mixt 无法独立发文 |
| 引入**唯一的外部依赖** | 登录授权需要一次性的 OAuth 中转点。它不是本站的常驻服务，但确实是本项目第一个"不在自己完全掌控内"的组件 |
| 产生字段漂移风险 | 网页端表单字段与文章元数据 schema 必须保持一致，改一处要同步改另一处 |
| 需要 Mixt 成为仓库协作者 | 私有仓库免费版协作者无上限，技术上无障碍 |
| **没有解决的遗留问题** | 它解决了"怎么写、怎么提交"，**但没解决"怎么上线"** —— 因为构建只能本地做，Mixt 提交后仍需 UU 执行一次构建上传。已作为待确认项记入 PRD 3.1 |

**为什么选它而不是另外两条路**

| 候选 | 未选原因 |
|---|---|
| UU 代为提交 | 每篇文章都要经 UU 的手，与 G6"Mixt 独立发文"冲突 |
| 教 Mixt 用 git | 与"Mixt 不接触代码与命令行"直接冲突 |
| 自建内容管理后台（数据库 + 常驻服务） | 与"无服务器端常驻进程"的硬约束冲突，且与 Markdown 文件链路产生双真相源 |

**为什么 Decap 与本项目形态相容**：它是构建期生成的**静态管理界面**，通过仓库接口直接提交 Markdown 文件，不引入本站的常驻服务，也不产生数据库 —— 与既有的"Markdown 文件即内容"链路完全一致。

### 7.3 内容合规规则与备案主体的责任

**背景**：站点以 **UU 个人**为主体备案 → 网站内容的法律责任落在 UU 身上。而 Mixt 面是二进制安全方向的 PWN 内容。

**用户选择**：**内容正常上，措辞做收敛**（而非不做、或改方向）。

由此产生两条产品约束：

1. **PRD 3.7 的 5 条措辞规则**（不附可直接使用的 exploit、环境自建、文首合规声明、标题避开敏感词、CTF writeup 可留但不放完整可复用 exp）
2. **UU 的合规否决权**（PRD 2.2）—— 这一项**刻意打破了"分栏自治下互不干涉"的对称性**，理由是备案主体的法律责任无法通过内部分工转移。同时限定了行使方式：必须说明依据的具体条款，不做无理由干预。

### 7.4 备案相关的事实修正

以下三处是**原 PRD 写错的事实**，不是需求变化：

| 位置 | 原写法 | 实际 | 原因 |
|---|---|---|---|
| 域名状态 | "已有域名，未备案" | **域名当时未注册**，现已注册 | 初稿把"已有域名"与"域名已注册"混为一谈 |
| 服务器 | 阿里云 **ECS** | 阿里云**轻量应用服务器**（上海 / Ubuntu 24.04 / 2核2G / 不限流量） | 采购阶段重新选型 |
| 备案归属 | 未记录 | **湖南省通信管理局**（按主体证件所在省，非就读地） | 初稿按"在南京读书"推断为江苏管局，**属未核实即下结论的失误** |

**选轻量的理由**（与"失败可见性"这条通用教训一致）：ECS 券后 0 元看着最便宜，但其带宽是**按使用流量计费** —— 被刷流量时不会报错、不会告警，只在月底账单上体现，与已被否决的双远端部署属同一类**静默失败**。轻量的"不限流量"买的是确定性。

**另一条必须记住的备案约束**：首次备案期间**必须暂停域名解析**，未备案的网站不得对外开通访问。开发预览只能走 IP + 非标准端口。

### 7.5 「关于本站」页：由不做改为要做

**用户决定**：要做独立页面，**入口页放一行小字支持跳转**。

**这是一次撤销**，记录在此以免日后困惑为什么 PRD 里它从"非目标"变成了需求。

| 项 | 内容 |
|---|---|
| 原决策 | **非目标**（不做独立"关于本站"页），理由是站点级说明可以融进入口页底部 |
| 现决策 | **要做 `/about/`**，入口就是入口页底部那一行小字 |
| 为什么不冲突 | 原决策反对的是"单独开页"，而现方案的入口依然是那行小字 —— 变化在于它现在**可点进去**，而不是只能挤在入口页底部 |

**新增的边界规则**

| 规则 | 理由 |
|---|---|
| 只由入口页底部小字进入，**不做导航栏入口**、不进两面的面内导航 | 站点的视觉重心是"两面"，公共项一旦进入导航栏就会稀释"两面隔离"的观感 |
| 关于本站页讲**站点**，作者页讲**个人** | 两者不重复内容。前者解释"这是什么站、为什么这么组织"，后者介绍"我是谁" |

### 7.6 AI 角色定为两个

**用户决定**：**master + UI 设计**，两个就够。

| 角色 | 承担 |
|---|---|
| **master** | 文档、流程、决策记录、任务派发。**不写代码** |
| **UI 设计 agent** | 全部工程实施 |

**一处需要说明的偏差（已写入文档并在交付时说明）**：实施 agent 的职责实际**比"UI 设计"这个名字宽** —— 除了界面与交互，还包括内容管线（schema、校验、构建脚本）、部署脚本、网页上传入口配置。这些不是 UI 工作。

**处理方式**：保留用户给的名字，但在 AGENTS.md §3 的职责列里把范围写全，避免将来这个 agent 因为"名字里只有 UI"而漏掉管线与部署部分。

### 7.7 特效禁令松绑：「常驻禁止，转场瞬间允许」

**用户决定（2026-09-13，Demo 动效评审后）**：入口页翻牌与面间翻转要有更强的视觉冲击力——粒子爆发、冲击波、全屏闪光——并要求修订 PRD 4.2 的原禁令。

| 项 | 内容 |
|---|---|
| 原条款 | 「禁止模糊、发光、渐变叠加、粒子等特效」（4.2，v1.0 起） |
| 现条款 | 拆为两条：**常驻特效仍禁止**；**转场瞬间允许**粒子爆发、同心冲击波、卡片主题色微发光、短暂全屏闪光 |

**原禁令针对的是什么**：制定原条款时担心的是"博客沦为特效展示页"——常驻的粒子背景、鼠标拖尾、发光边框会持续分散阅读注意力、消耗性能，且与"两位作者都不熟 web、要零运维"的约束相冲突。

**为什么转场瞬间可以放行**

| 理由 | 说明 |
|---|---|
| 不稀释阅读体验 | 特效只存在于转场的约 1.3 秒内，正文阅读状态（静止页面）完全无特效，原禁令保护的场景不受影响 |
| 翻转是本站的**产品签名** | 双面翻转是核心设计（PRD 4.2/4.3），转场冲击力直接服务于"翻牌"这一仪式感，不是装饰性堆砌 |
| 性能可控 | 粒子/冲击波/闪光元素全部由 JS 动态创建、`animation.finished` 后移除，且**只动画 `transform` 与 `opacity`**（合成层属性，不触发重排重绘）；峰值同时存在的粒子约 100 个，远低于低端机可承受范围 |
| 降级链完整 | `prefers-reduced-motion` 与无 JS 场景一律跳过全部特效，与原降级表（4.2）一致 |

**边界条件（写进 PRD 的判定标准）**

| 判定 | 规则 |
|---|---|
| 常驻 vs 瞬间 | 页面静止时不得存在任何特效元素；特效元素的 DOM 必须在转场结束后移除 |
| 闪光上限 | 全屏闪光峰值不透明度 ≤ 0.2、时长 ≤ 700ms，避免刺眼与光敏风险 |
| 属性白名单 | 一切特效只动画 `transform` / `opacity`（发光用的 `box-shadow` 仅出现在转场期间的卡片上，转场结束随状态类移除） |

**通用教训的又一条印证**：原条款是"一刀切禁止"，实际合理形态是"分场景约束"——这和 §2 中"私有仓库 ≠ 私有网站"的澄清是同一类：**把笼统的禁令拆成场景化规则，比绝对禁止更可执行**。

### 7.8 面视觉背景：把「Hero 图 + 常驻虚化」从特效里摘出来

**用户决定（2026-09-13，v4 Demo 评审后确认）**：确认按 7.7 的思路继续修订 PRD——面首页用整屏高清封面开场，下滑进入正文，正文区以同一张图**常驻虚化**铺底。

**冲突点**：PRD v1.3 的「常驻禁止」里写着"模糊"，而常驻虚化背景正是 `filter: blur()`，字面冲突。

**裁决：豁免。理由是它压根不在原条款针对的问题域里**

| 原条款针对 | 常驻虚化背景的实际情况 |
|---|---|
| 常驻特效会**持续分散阅读注意力** | 虚化背景是静态底图，不含任何运动，注意力不会被拉走 |
| 常驻特效会**持续消耗性能** | `filter: blur` 只影响合成层，静止后不再重绘；图片为构建期压缩的静态资源 |
| 特效是**装饰性堆砌**，可删 | 背景图是作者的人格化表达（UU 的 Minecraft 日落 / Mixt 的蓝调桌面），删掉等于删掉一面的身份标识 |
| 与"两人都不熟 web、零运维"冲突 | 只是两张静态图 + 两个 CSS 变量，无新增依赖与运维负担 |

**因此新增一条判定原则**

> **「是不是特效，看它是否动，而不是看它用了哪个 CSS 属性。」
> `blur` 用在**静止背景**上是视觉风格；`blur` 用在**跟随鼠标/持续动画**的元素上才是特效。**

这条原则同时解释了为什么 v1.3 的「转场瞬间允许」是合理的：那里是"动"，但动得短、动完即删；这里是"不动"，所以常驻也无妨。

**写进 PRD 的三条约束（不是放任）**

| 约束 | 理由 |
|---|---|
| 必须叠 veil，正文对比度 ≥ 4.5:1 | 背景图不可控（用户随时换图），可读性不能赌在"这张图恰好够暗"上 |
| 图片加载失败回退纯色 | 与"零运维"一致——不允许出现"图挂了页面就没法看"的状态 |
| 单图 ≤ 400KB、Hero 图预加载 | 2C2G 服务器 + 移动流量；Hero 是首屏元素，不能出现图片迟到导致的空白 |

**又一条印证**：这是 7.7「分场景约束优于绝对禁止」的第二次应用——两次都发生在同一条条款（4.2）上，说明**当初那条禁令写得过粗**。若后续再出现类似争议，优先考虑"条款是否该拆"，而不是"这次要不要破例"。

### 7.9 写作台形态：按 Demo 定稿，Decap 方案降级为后端候选（2026-09-14）

**背景**：写作台（原 3.8「网页上传入口」）的交互原型已在 Demo 中完成并经用户逐条确认，形态与原定 Decap CMS 方案出现实质差异。PRD v2.0 据此重写 3.8。

**用户逐条确认的需求（即决策依据）**

| 需求 | 决策 |
|---|---|
| 「提交后直接在网站里看到，不需要审核」 | **提交即发布**，无审核环节（与 2.5「不设审核」一致；草稿不进站点） |
| 「进入写作台需要输入密码，两开发者不同密码」 | 登录门双密码 → 独立工作台页；**身份锁定本人面**（技术强制，优于 Decap"靠约定"） |
| 「没必要让作者写 url，自动生成即可」 | **slug 自动生成**，作者不接触 URL 概念；发布后冻结 |
| 「做好写作台的分类」 | 每面**自维护分类**（增改删、改名同步文章标签、点击展开时间线） |
| 「媒体有什么用」 | 明确为**配图引用生成器**（选图 → 预览 → 复制仓库路径引用） |

**与原方案的关系**：原 3.8 选定 Decap CMS 是"当时的手段"；Demo 验证后发现**作者真正需要的是上面这五条交互**，而手段（Decap / GitHub API 直提 / 本地 git）不影响 UI。因此 PRD v2.0 把 3.8 改写为「写作台：UI 按 Demo 定稿 + 后端选型开放」，Decap 从"方案"降级为"候选之一"。

**正式实现时的关键动作**：把 Demo 的本地内容层（`demo-store.js`，localStorage）替换为真实数据源（仓库 Markdown + 构建期读取），**内容层暴露的接口语义保持不变**——这就是 Demo 留给正式开发的最重要接口契约。

**教训**：需求文档写"手段"（Decap CMS）而不是"目的"（作者在网页上独立发文）时，手段一旦被更好的原型推翻，文档就得大改。**PRD 应该约束目的与验收，手段让原型去发现。**

### 7.9 流程整体减负：撤销分阶段协作

**用户决定（2026-09-14）**：这是一个小博客开发，**不用分阶段那么重**；所有开发工作交给 UI 窗口 agent；完工后的部署交给 master。

**这是一次对既定流程的撤销**，记录在此以免日后有人拿着流程文档来"纠正"项目。

| 被撤销的约定 | 原出处 | 现状 |
|---|---|---|
| 四阶段串行、每阶段等人确认 | 《基于 Agent 的协作开发流程参考》§0 C2 | **删除**。开发节奏由 UU 与 UI 窗口自主把握 |
| 里程碑门禁（M0–M9 的"完成判定"） | PRD §8 | **降级为开发顺序参考**，不再构成门禁 |
| 里程碑三连提交（feat + test + docs） | 流程文档 C5 | **删除**，保留 Conventional Commits 与一文一提交 |
| 强自测的证据归档仪式（`scripts/` + `docs/*-self-test/`） | 流程文档 §5 | **简化**为"每次交付附可验证的结果（截图/输出/日志）" |
| "多 agent 分工"的 formal 要求 | 流程文档 §1.2 | 定稿为两个 AI 角色：**master（文档+部署）** 与 **UI 窗口 agent（全部开发）**，不并行 |

**为什么可以撤**：流程文档是为多人、多会话、长周期项目设计的。本项目是一位开发者（UU）+ 一个实施 agent + 一个内容作者（Mixt，不碰代码），全部工作在几个文件、几十个提交内完成——**流程的复杂度必须匹配项目的规模**。

**没有一并撤掉的（因为这些不是流程，是边界与纪律）**

| 保留 | 理由 |
|---|---|
| SSOT 文档分工（01 只写要什么 / 02 只写为什么） | 已在实际运行中被 UI 窗口沿用（7.7、7.8 均按此格式追加），且是防止重复讨论的唯一手段 |
| 文件分区与"先做一面、另一面镜像" | 两面隔离是产品需求，镜像纪律是保证一致性的唯一方法 |
| Conventional Commits 与一文一提交 | 仓库历史已在用，且它是可追溯性的最低成本形态 |
| 安全与合规纪律 | 与流程无关，与备案主体责任有关 |
| 踩坑即时沉淀 | 成本近零，收益在第二次遇到时 |

**新确立的部署职责**：部署由 **master** 负责，触发条件是"UI 窗口完工并经 UU 验收"。方式仍是本地构建 + `deploy.sh` 上传——这是 7.4 与 §2.3 已论证过的形态，本次只是明确了**谁来执行**。

**留了一道保险**：PRD §8 的里程碑表**没有删除**，只是降级为开发顺序参考。若日后项目规模变大（如 E1 AI 助手落地、第三位作者加入），可以直接把这张表重新升格为门禁，不必从零重建。
