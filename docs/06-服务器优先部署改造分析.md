## 0. 结论速览

1. **访客路径今天起就 100% 走服务器，不需要任何修改**——审计证实产物里没有 CDN、没有 GitHub 资源引用（§1）。「GitHub 慢」影响不到读者。
2. **真正被 GitHub 卡住的是作者的写入路径**：写作台目前直连 `api.github.com`（国内访问慢且不稳）。要改的是这一段。
3. 推荐方案 **B（服务器为主库 + 写作台换传输层 + GitHub 定时镜像）**：改动集中在写作台的传输层与服务器侧一个小服务，**访客路径、页面代码、内容层接口全部不动**。

---

## 1. 现状依赖审计（2026-09-14 实测）

对构建产物全量扫描（`grep -rEoh 'https?://…' dist`）：

| 外部域名 | 出现次数 | 是什么 | 访客会请求吗 |
|---|---|---|---|
| `beian.miit.gov.cn` | 88（每页 1 条） | 页脚备案号链接（工信部要求） | 仅点击时 |
| `uuandmixt.com` | 14 | canonical / RSS 地址（自己的域名） | 否（元数据） |
| `github.com` | 1 | UU 作者页的个人主页链接 | 仅点击时 |
| `api.github.com` | 1（在 `gh.js`） | **写作台的提交通道** | **否**（只有作者进 `/admin/` 才加载） |

结论：

- 字体是系统字体栈、背景图 / 头像 / 全部脚本样式均为本地文件，`dist/` 自包含。
- **读者从服务器拿到一切**。GitHub 从未出现在访客的请求路径里——这条已经成立，不需要改造。
- GitHub 依赖集中在两处：**① 写作台写入通道**（每次发文都要过 GitHub API）；**② 内容与代码的源库**（构建输入在 GitHub 上）。

## 2. 三个候选形态

| | A · 维持现状 | **B · 服务器为主库（推荐）** | C · 全服务端化 |
|---|---|---|---|
| 内容主库 | GitHub | **服务器**（git bare 仓库） | 服务器（文件目录） |
| 写作台写入 | GitHub API（慢 / 可能不可达） | **服务器小服务 API**（同机房，快） | 服务器小服务 API |
| GitHub 角色 | 源库 | **异地备份（镜像）** | 异地备份 |
| 构建 | 本地 | **本地**（拉取服务器内容后构建） | 服务器（**违背 2C2G 不构建的既有决策**，OOM 风险） |
| 新增服务端组件 | 无 | 一个小服务（写入 API；可与桌宠 E1 合并） | 构建管线 + 服务 |
| GitHub 不可达时 | 作者写不了文 | **作者照常发文**（构建/发布延后） | 照常 |
| 改动量 | 0 | 中（传输层 + 服务器侧） | 大 |
| 判定 | 不满足「GitHub 只作备份」 | **推荐** | 不推荐（内存风险 + 改动过大） |

> 方案 C 被否的关键：技术方案既有决策「构建只在本地（服务器 2C2G）」；Astro 构建在 2G 内存机器上有 OOM 风险（当初否决 Next SSR 的同一原因）。

## 3. 方案 B 的目标架构

```
作者（UU / Mixt）                     本地（构建机）                      服务器（2C2G）
────────────────                    ──────────────                    ────────────────
写作台 /admin/desk/                  git pull  ←──────────────┐        Nginx ──→ dist/（静态站，访客访问）
   │  HTTPS + 作者 token              npm run build            │            ↑ rsync 上传
   ▼                                 node check-pages         │        站点小服务（唯一常驻进程）
   写入 API ──────────────────────────────────────────────────→ git commit
                                     ./deploy.sh（rsync dist） │        git bare 主库
                                                              │            │ cron：push --mirror
                                                              └────────────┴──→ GitHub（异地备份，可断）
```

- **写入**：作者 → 服务器 API（毫秒级）→ 服务端 commit 进服务器主库。GitHub 挂了完全不影响发文。
- **发布**：本地拉取服务器主库 → 构建 → 自检 → rsync `dist/` 上服务器。仍是 3 条命令（G4 不变）。
- **备份**：服务器 cron 定时 `git push --mirror github`（失败只告警不阻塞）；服务器磁盘故障时从 GitHub clone 即可整体恢复。

## 4. 改动清单（拍板后实施）

### 4.1 写作台：传输层替换，逻辑零改动

当初按「接口语义」抽象的回报在这里兑现。`desk.js` 对后端的全部依赖只有 8 个函数（实测）：

```
getSession / clearSession / isMock / listDir / readFile / writeFile / removeFile / uploadBinary
```

新增 `public/scripts/admin/server.js` 实现**同一接口**（登录改为「服务器地址 + 作者 token」，`?mock=1` 假后端机制保留用于自测），`desk.js` 一行不改。登录页的取 token 提示文案同步替换（GitHub PAT → 服务器 token 的获取说明）。

### 4.2 服务器小服务（唯一新增的常驻组件）

职责与约束（写入 API）：

| 项 | 规格 |
|---|---|
| 接口 | `POST /api/write`（文本 / 图片 multipart）、`GET /api/read`、`GET /api/list`、`DELETE /api/file`；与 gh.js 的语义一一对应 |
| 鉴权 | 每作者一个 token（服务端只存 hash）；**face 由 token 推导，接口不接受 face 参数**（沿用「越面写入做不到」的强制） |
| 路径白名单 | 仅 `src/content/<face>/**`、`src/config/categories-<face>.json`、`public/images/<face>/**`；拒绝 `..` / 绝对路径 / 符号链接 |
| 限流与配额 | 每 token 限频；单文件上限（Markdown ≤ 200KB、图片 ≤ 2MB） |
| 版本化 | 每次写入即 `git commit`（作者、时间、改动路径天然入审计日志） |
| 失败可见性 | 写失败必须返回明确错误（PRD 6.1 既有条款） |
| 形态 | 单进程（Go / Node / Python 皆可）、systemd 守护、内存 < 50MB、只监听本机由 Nginx 反代 |

### 4.3 git 拓扑与发布流

- 服务器：`/srv/uum/repo.git`（bare，主库）+ 工作副本（服务 API 写入并 commit）。
- 本地：`origin` 改指服务器（SSH）；`github` 作为第二个 remote 仅用于查看历史。
- GitHub：服务器 cron（如每 6h）`git push --mirror`，失败写入告警日志。
- **发布流（G4 仍为 3 条命令）**：`git pull` → `npm run build && node scripts/check-pages.mjs` → `./deploy.sh`。
- 注意：服务器上的内容目录**不得**位于 Nginx 站点根下（防止仓库内容被直接下载）。

### 4.4 图片与资源

- 写作台媒体面板改传服务器 API（multipart 直传），落 `public/images/<face>/`；正文引用路径 `/images/<face>/文件名` **不变**（URL 空间稳定，已发布的文章无需回改）。
- 访客侧资源全部随 `dist/` 走 Nginx：本站无 CDN、无 webfont、无 GitHub 资源引用（§1 审计），**无需任何改动**。

### 4.5 明确不改的部分（防过度改造）

- 页面代码、卡牌翻转、面视觉、内容层接口语义（`content-layer.ts`）——与部署形态完全解耦。
- 搜索索引 / RSS / sitemap——构建产物，自包含。
- 构建仍在本地（2C2G 决策不变）；`deploy.sh` 归 master，前端只约定接口。

## 6. 风险与对策

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| 1 | 写入 API 成为攻击面（暴露在公网） | 高 | HTTPS only + token 鉴权 + 路径白名单 + 限流 + 仅 Nginx 反代（服务只听 127.0.0.1）；8080 预览期不开写入 API |
| 2 | 两位作者并发改同一分类配置 | 中 | 服务端逐请求加锁（串行化）；git 历史可回滚；冲突时后写者收到明确报错重试 |
| 3 | 服务器磁盘故障 → 主库丢失 | 中 | GitHub 镜像即灾备：`clone from GitHub → push to 新服务器` 恢复流程写进 README |
| 4 | 镜像滞后导致误以为 GitHub 是最新 | 低 | 文档明确「服务器为主库」；镜像 cron 失败告警 |
| 5 | 小服务内存挤占静态站 | 低 | 单进程 < 50MB（PRD 已为桌宠预留 200MB 预算内） |
| 6 | 本地构建机依赖服务器可达 | 低 | 构建前拉取失败即显式报错（失败可见性条款）；极端情况可临时从 GitHub 镜像拉取（数据略旧） |

## 8. 衔接：桌宠（E1）与友链（新增 E8）

两项均按既有协作模式执行：**你先在 demo 里做形态 → 验收 → 我按 demo 接线到正式站**。本节先把规划登记进 PRD，避免丢失。

### 8.1 桌宠 = 已有 E1「站内 AI 助手」，本次补充三点

1. **「回答严格限制在博客范围内」的落地方式**（与 PRD E1 的 RAG 描述一致，补充实现锚点）：
   - 知识库直接复用**搜索索引** `search-index.json`（构建期生成、只含已发布文章，天然是"博客范围内"的语料）；检索不到就明确说"这超出了博客内容"。
   - LLM 转发端点（Key 只在服务端）+ 限流——若采用方案 B，与写作台写入 API **合并为同一个站点小服务**（一个进程、一份运维）。
   - System prompt 硬约束 + 输出侧兜底过滤；敏感问题（尤其 Mixt 面的安全内容）只做站内文章的转述与链接，不展开站外知识。
2. **前置顺序不变**：E1 的门槛是「首期上线并稳定运行后」，先做零 API 成本的静态检索版验证需求。
3. 形象立绘、交互形态 → **等你的 demo**。

### 8.2 友链 = 新增扩展项 E8

- 方向：友链页（互相跳转的个人博客）。数据形态建议参照分类配置：一个 JSON 配置文件（名称 / 地址 / 头像 / 简介 / 归属面或全站），构建期渲染静态页——**无需任何服务端**。
- 待你的 demo 定：入口位置（页脚 / 独立页 / 两面各自）、卡片形态、是否需要友链申请说明与下架规则。
- 合规注意：友链是外链，需在页脚或友链页标注「外部站点与本站无关」；建议 `rel="noopener"`（是否 nofollow 由你定，友链通常不加）。
