## 0. 总览

| # | 关键决策 | 一句话 |
|---|---|---|
| 1 | 站点形态 | **Astro 静态多页（MPA）**，不做框架 hydration；所有交互用原生 JS 模块 |
| 2 | 内容层 | 仓库 Markdown（Astro Content Collections）+ 构建期 zod 校验；**接口语义与 demo-store.js 一一对应**（§2） |
| 3 | 翻转与特效 | demo 的 DOM/WAAPI 方案原样迁移为独立脚本模块，**不引入任何动画库**（§4） |
| 4 | 写作台 | UI 按 Demo 原样迁移；后端推荐 **GitHub Contents API 直提**（§5 供拍板） |
| 5 | 性能 | SSR 后公开页面 JS 从 42KB 降到 **≈ 6–8KB**；构建期用脚本强制卡预算（§4.4） |

## 2. 内容层替换设计（核心）

### 2.1 原则

Demo 用 `demo-store.js`（localStorage）模拟内容层。正式实现改为「**仓库 Markdown + 构建期读取**」。两条铁律：

1. **接口语义不变**：`demo-store.js` 暴露的每个函数在正式实现里都有同义对应（§2.2）。
2. **公开页零内容层 JS**：面首页/归档/分类/详情全部 **SSR**（构建期生成 HTML），浏览器不再下载 18.1KB 的 store——这是把面页 JS 从 42KB 砍到 ≈6KB 的根本原因。

### 2.2 接口语义映射表（Demo → 正式实现）

| `demo-store.js`（localStorage） | 正式实现（Content Collections） | 调用方 |
|---|---|---|
| `published(face)` → 非草稿、featured 在前、日期倒序 | `getCollection(face, ({data}) => !data.draft)` + 同规则排序 | 面首页/归档/分类（SSR） |
| `allPosts(face)` → 含草稿 | `getCollection(face)` 全集（仅写作台通过后端读，**不进构建产物**，见 §2.4 注） | 写作台 |
| `getPost(id)` | `getCollection` 按 `slug` 查找 | 详情页（SSR） |
| `addPost(data)` | 写作台保存 → 写入 `src/content/<face>/<slug>.md`（落点见 §2.3） | 写作台 |
| `updatePost(id, patch)` | 覆写同文件（slug 冻结，改 slug 需重定向映射，PRD 4.1） | 写作台 |
| `removePost(id)` | 删除文件 | 写作台 |
| `categories(face)` | 读 `src/config/categories-<face>.json` | 分类页/写作台 |
| `addCategory / updateCategory / removeCategory` | 写该 JSON 文件；**改名时同步改该分类下所有文章的 `category` 字段**（语义与 Demo 一致） | 写作台 |
| `categoryCount(face, name)` | 集合内计数 | 分类卡片 |
| `tags()` | 遍历集合聚合（共享标签池，PRD 3.6） | 标签页 |
| `reset()` / `seed()` | 不适用（真实数据即权威） | — |

### 2.3 Markdown 文件放置与写作台「保存提交」的落点

**文件位置**

```
src/content/uu/<slug>.md        # UU 面文章
src/content/mixt/<slug>.md      # Mixt 面文章
```

frontmatter 即 §3 字段表；正文为标准 Markdown（Astro 内置 remark/rehype 渲染，含 GFM 表格）。

**「保存提交」在两种后端选型下的落点**

| 后端 | 保存动作 | 写入位置 | 后续 |
|---|---|---|---|
| **A · Decap CMS** | Decap UI（替换为 Demo 形态的自定义 UI 亦可）→ Decap 代理 → GitHub Contents API | `main` 分支 `src/content/<face>/<slug>.md`（草稿 = `draft: true`，**不建分支不做 PR**） | 与 3.1 发布链路汇合：UU 手动 `deploy.sh`（方式 A）或 CI（方式 B） |
| **B · GitHub API 直提** | 工作台页（静态 JS 模块）直接调 `PUT /repos/{owner}/{repo}/contents/{path}`，作者 GitHub 身份经登录获取 | 同上：`main` 分支同路径 | 同上 |

两方案的**落点完全一致**（同一条路径、同一个分支、同一份 frontmatter）——因此 §5 的选型只影响「怎么进仓库」，不影响内容与构建。Demo 的工作台 UI 对两方案均可复用（通过 `scripts/admin/backend/` 的可替换模块隔离差异）。

### 2.4 构建期读取与校验

**读取**：`getCollection()` 在构建期把 `src/content/**` 读入内存；`content-layer.ts` 在其上实现 §2.2 的接口（SSR 调用）。生成路由由 `pages/<face>/posts/[...slug].astro` 的 `getStaticPaths()` 完成。

**校验（构建期强制，PRD 3.3）**

| 时机 | 机制 |
|---|---|
| schema 级 | `src/content.config.ts` 用 **zod** 逐字段声明（§3 字段表即 zod 规则的文档形态）；不合规则 `astro build` 失败，报错含**文件路径 + 字段名 + 期望值**（PRD 3.3 报错要求） |
| 交叉级 | 分类引用（`category` 须在本面 `categories-<face>.json` 中登记）、站内死链（自定义 remark 插件扫描站内链接）、slug 同面去重、`date` 不晚于构建日 |
| 兜底 | `scripts/check-schema.mjs` 提供「故意写错字段 → 必须失败」的自检用例（验收项 5） |

> **注**：草稿文章同样参与构建（`draft: true` 只被 `published()` 过滤，不进任何路由/索引/feed/sitemap），但**绝不能出现在构建产物中**——包括详情页路由、列表、`/data/` JSON、sitemap、RSS、搜索索引。这是"私有仓库 ≠ 私有网站"的具体落点（PRD 6.6）。

### 2.5 写作台的数据源（只读 vs 写入）

- **公开页**：纯 SSR，无 JSON 数据源。
- **写作台读路径**：**不走构建产物**（草稿不能暴露）——工作台页通过后端（Decap 自带读取，或 GitHub Contents API 列目录+读文件）实时读取仓库内容，与真实数据完全一致。
- **写作台写路径**：见 §2.3。保存成功后的「站点立刻可见」语义（PRD 3.1/2.5）在正式实现中等价于「提交进仓库即进入发布队列」；浏览器刷新看到新文章需要一次构建+部署（3.1 的 A/B 开放项）。

## 3. 文章字段表（PRD 3.2/3.3 的唯一依据）

> 以下表格是 **构建校验（zod）、写作台表单、RSS** 三处的唯一字段依据；任何字段变动必须三方同步（AGENTS §3 规则 1）。

| 字段 | 类型 | 必填 | 校验规则（构建失败条件） | 写作台表单 | RSS |
|---|---|---|---|---|---|
| `title` | string | ✅ | 非空，≤ 60 字符 | 文本框 | `title` |
| `slug` | string | ✅（**系统生成**） | 纯 `kebab-case`（`[a-z0-9-]+`）；同面唯一；**发布后冻结**（改 slug 需登记重定向映射） | **不显示**；英文标题自动生成、中文标题 `post-YYYYMMDD-xxxx` 兜底（可升级为中文转拼音） | `guid` |
| `description` | string | ✅ | 60–120 字符 | 文本框 | `description` |
| `date` | `YYYY-MM-DD` | ✅ | 合法日期，不晚于构建日 | 日期控件（默认今天） | `pubDate` |
| `updated` | `YYYY-MM-DD` | 可选 | 合法日期，晚于 `date` 时才显示 | 保存时自动更新 | — |
| `author` | `uu` \| `mixt` | ✅ | 枚举两值；**必须与所在目录一致**（`content/uu/` 里只能是 `uu`） | 只读（身份锁定） | `author` |
| `authors` | `[uu\|mixt]` ≤2 | 可选（仅合写） | 双值时并列展示 | 不显示（合写由主笔本地改） | — |
| `category` | string | ✅ | 必须在本面分类配置中已登记；中文或英文均可（短名归分类配置的 `slug` 字段管） | 下拉（本面分类）；空分类面禁用并提示 | `category` |
| `tags` | string[] | 可选 | ≤ 5 个，无空值 | 逗号分隔输入 | `category`（追加） |
| `cover` | `/images/...` 路径 | 可选 | 文件必须存在（媒体面板生成引用） | 媒体面板插入正文，不做独立字段（首期） | — |
| `draft` | boolean | 可选（默认 `false`） | — | 复选框「存为草稿」 | 草稿不出现 |
| `featured` | boolean | 可选（默认 `false`） | — | 复选框「置顶」 | — |

**生成与派生字段（不写入文件）**：`words`（正文字数）、`minutes`（≈270 字/分钟）、`href`（路由）。

## 4. 卡牌翻转 + 面视觉背景的迁移方案

### 4.1 组件化拆分

| Demo 实现 | Astro 迁移 | 说明 |
|---|---|---|
| `.page-card`（body 直接子级，包裹页头+正文+页脚） | `Layout.astro` 固定结构：`<body>` → `.page-bg`/`.page-veil`（仅面页）→ `.page-card`（页头/内容/页脚） | body 挂 `data-face` / `data-flip-to` / `data-default-mode`（页级默认主题） |
| `flip-out` / `flip-in`（CSS keyframes，±89°） | `styles/shell.css` 原样迁移（`perspective: 2400px` 不变） | `flip.ts` 负责加类与跳转 |
| 高光带 `.gloss`（跨页 sessionStorage 衔接） | `flip.ts`：翻出面 `UUMFX.gloss("out")` → 写 `uum-flip-in` → 跳转；目标页内联脚本置 `flip-in-pending` 防闪帧，核心脚本播放后半程 | 粒子只在入口页；面页翻转只有高光（与 Demo 一致） |
| 粒子/喷泉/冲击波/闪光（WAAPI） | `scripts/fx.ts` 原样迁移（PALETTES 取主题变量），**仅 `index.astro` 加载** | 转场结束即移除 DOM；`prefers-reduced-motion` 与无 JS 全跳过（PRD 4.2） |
| 翻面控件（按钮 / Alt+←/→ / 触屏滑动） | `FlipControl.astro` + `flip.ts` | 直接访问面页不播动画（PRD 4.2 URL 同步） |

### 4.2 面视觉背景（Hero + 常驻虚化 + veil）

| 层 | 迁移 | 说明 |
|---|---|---|
| Hero 整屏封面 | `Hero.astro`：`.hero-bg`（`--face-bg-img` 经 CSS 变量按面注入）+ `.hero-veil` + 内文 + 下滑锚点 | 封面图用 Astro 的 `sharp` 生成 **WebP + srcset（1280/1920/2560）**；`<link rel="preload">` 保 LCP（验收项：LCP < 2.5s） |
| 常驻虚化背景 | `Layout.astro` 的 `.page-bg`（同图 `blur(26px) brightness(1.24) saturate(1.05)`）+ `.page-veil`（明暗各一套） | 仅 `body.has-hero` 的面页挂载；**图片加载失败回退纯色**（PRD 4.2 面视觉条款的降级要求） |
| 入口页背景 | `.entry-bg` / `.entry-veil`（`entry-has-bg`） | 同处理 |
| 对比度兜底 | 构建期 `scripts/measure-js.sh` 附像素采样脚本（沿用 Demo 自测方法），输出入口页/封面文字对比度 ≥ 4.5:1 的证据 | veil 与提亮参数以 Demo CSS 为准（brightness 1.24 / veil 0.55/0.62 等） |

### 4.3 不引入动画库的理由

Demo 的特效全部为「CSS keyframes + WAAPI（transform/opacity）+ 静态 DOM 注入」，总共约 4KB，无滚动监听、无 rAF 循环。引入任何动画库（GSAP 等）都会单独吃掉 20–60KB 预算且没有功能增益——**否决，维持原生实现**（与 PRD 6.2 否决重量级动画库一致）。

### 4.4 性能预算的守法门禁（实测口径）

| 页面 | 构成 | 预算（PRD 6.4/7.2） | 预估 | 依据 |
|---|---|---|---|---|
| 入口页 `/` | core（模式/toast，≈1.2KB）+ 翻牌状态机（≈2KB）+ `fx.ts`（≈4KB） | **≤ 15KB** | **≈ 7–9KB** | demo-entry.js 实测 8.3KB 包含粒子全集，迁移时剔除无用分支 |
| 面首页/文章页 | core + `flip.ts`（≈1KB）+ `toc.ts`（≈1.5KB）+ `resize.ts`（≈1KB） | **< 30KB** | **≈ 5–7KB** | SSR 后 demo 的 42KB 中 store（18.1KB）与内容层渲染函数（≈10KB）全部消失 |
| 写作台 | desk 模块 + 后端模块 | 不设预算（管理页，PRD 预算仅针对公开页面） | ≈ 20–25KB | demo 写作台内联脚本实测 18.3KB |
| 全部 JS 压缩方式 | Astro 打包 minify + 静态 gzip/brotli（Nginx `gzip_static`） | — | 未压缩口径即预算口径（PRD 原文） | — |

**门禁**：`scripts/measure-js.sh` 在构建后对 `dist/` 各路由的 JS 体积做断言（未压缩字节数），超限非零退出——每次部署前必跑（对接 AGENTS §5 的「失败必须可见」）。

## 5. 写作台后端选型建议（供拍板）

| 维度 | A · Decap CMS | **B · GitHub Contents API 直提（推荐）** | C · 本地 git 工具 |
|---|---|---|---|
| 与 Demo UI 的兼容 | 可用自定义 UI（Decap 提供注入点）或直接用其原生 UI | **Demo UI 原样复用**（backend/github-api.ts） | 仅 UU 可用，不满足 G6 |
| 身份与权限 | GitHub OAuth；Decap 开源版**无按集合的细粒度权限**（"只管自己面"靠约定） | 作者各自的 **scoped PAT**（仅 Contents: rw，仅本仓库）；"只管自己面"由工作台身份锁定 + token 归属双重保证 | — |
| 新增外部依赖 | **唯一外部依赖**：OAuth 中转（Netlify Identity / Cloudflare Worker 自建二选一） | **零新增基础设施** | — |
| 凭据安全 | token 经 OAuth 中转，不落前端 | PAT 由作者**自行粘贴**、存于自己浏览器 localStorage；scoped + 可随时吊销；前端产物不含任何凭据（符合 PRD 6.6） | — |
| 草稿语义 | 支持（`draft: true` 落 frontmatter） | 同左 | — |
| 提交路径 | Decap 代理 → main | Contents API → main（不经 PR，与 AGENTS §4.3 一致） | 本地仓库 |
| 风险 | OAuth 中转挂了则全体无法提交；版本升级需跟踪 | PAT 粘贴对 Mixt 有一次性教学成本；PAT 若泄露 → 影响仅限本仓库 contents 权限，吊销即可恢复 | — |
| 工作量 | 部署 OAuth 中转 + 配置 | 实现约 80 行的 API 封装 + 登录表单（粘贴 PAT） | — |

**建议**：**首选 B**。理由：两名作者、一个私有仓库、发布本身就要构建部署——引入 OAuth 中转服务解决一个并不存在的高频需求不划算；PAT 的教学成本是一次性的，而 OAuth 中转是要长期维护的。
**退路**：若 Mixt 试用 PAT 流程后觉得别扭，再切 A（UI 不变，只换 backend 模块）。C 不满足 G6，否决。

## 7. 风险与对策

| # | 风险 | 概率/影响 | 对策 |
|---|---|---|---|
| 1 | **草稿泄露**：`/data/` JSON 或搜索索引把 `draft: true` 文章带进公开产物（写作台曾要求「含草稿列表」） | 中 / **高**（违背"私有仓库 ≠ 私有网站"） | 写作台读路径**只走后端 API**，不为写作台生成任何构建产物 JSON；`published()` 过滤器同时作用于路由、列表、RSS、sitemap、Pagefind；`check-schema.mjs` 增加「草稿文章不得出现在 `dist/` 任何路径」的断言 |
| 2 | **特效迁移走样**：粒子/卡牌翻转/高光在组件化后出现时序错乱（如翻入页白闪、粒子挂在错误层） | 中 / 中 | 逐页对照 Demo 做**截图级回归**（沿用 Demo 的自测方法：无头 Chrome + 探针 + `document.title` 读数）；`flip-in-pending` 内联脚本放在 `<head>` 保证翻入页不闪帧；reduced-motion 与无 JS 用例纳入验收 |
| 3 | **性能预算失守**：首屏 JS 悄悄超过 30KB（写作台之外的页面误挂 desk 模块） | 中 / 中 | §4.4 的门禁脚本在部署前断言体积并打印明细；admin 脚本与公开页面脚本**物理隔离**（`scripts/admin/` 独立目录，入口页仅 `fx.ts`）；每期迭代跑 `measure-js.sh` 并把数字写进提交信息 |
| 4 | **图片体积与 LCP**：Hero 封面是首屏最大元素（bg-uu 268.7KB / bg-mixt 361.9KB），大图拖慢 LCP（预算 < 2.5s） | 高 / 中 | sharp 生成 WebP + 3 档 srcset，首图 `preload` + `fetchpriority="high"`；内容图片 `loading="lazy"` + `decoding="async"`；单张原图 ≤ 400KB 的规则写进媒体面板提示（PRD 4.2 面视觉条款） |
| 5 | **内容层替换后接口漂移**：正式实现的列表排序/草稿过滤与 Demo 不一致，用户以为"少了文章" | 低 / 中 | §2.2 的映射表作为 `content-layer.ts` 的注释与单测依据；用两篇精修文 + 6 篇种子文章做数据回归（构建产物与 Demo 列表逐条比对） |
| 6 | **后端选型返工**：PAT 流程 Mixt 不接受，被迫切回 Decap | 低 / 低 | UI 与后端以 `backend/` 模块隔离，切换不碰工作台 UI；§5 已声明退路 |
